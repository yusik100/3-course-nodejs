# Request-scoped контекст через AsyncLocalStorage замість протягування параметрів крізь шари

## Context and Problem Statement

Кожен HTTP-запит має технічний ідентифікатор (`X-Request-Id`), який потрібен у кожному лог-рядку, у тілі помилки й
у будь-якому шарі — від роута до репозиторію (spec-02, §5, AC-5). Якщо передавати його параметром, сигнатури всіх
функцій отримують технічну деталь, не пов'язану з бізнес-правилом, а кожне нове поле контексту (`traceId`,
`tenantId`) ламає ці сигнатури й тести. Питання: як зробити request-scoped дані доступними будь-де, не порушуючи
межі шарів зі spec-01 і не додаючи залежностей (ADR-0001)?

Окремо фіксуємо межу рішення: **керування залежностями** (хто створює репозиторії, сервіси, `db`) цим ADR не
змінюється — об'єктний граф збирається явно в composition root (`src/app.ts`), а інтерфейси передаються згори вниз
(spec-02, §2). Тут ідеться лише про **request-scoped контекст**.

## Decision Drivers

- Ізоляція бізнес-логіки: сервіси й репозиторії не знають про HTTP і не приймають `requestId` параметром.
- Мінімум залежностей: у `dependencies` лише те, що вже є (ADR-0001, spec-02).
- Незмінні сигнатури при додаванні нових полів контексту.
- Вбудований інструмент Node ≥ 24.13 (`engines`) — без поліфілів, native-збірки й сторонніх пакетів.
- Одна точка входу й один типізований аксесор — щоб рішення легко читалося й тестувалося.
- Перевірюваність: правило доводиться `grep` і тестами, а не «на слово».

## Considered Options

- Явна передача параметрів крізь усі шари (prop drilling / parameter threading)
- DI-контейнер зі scoped lifetime (`tsyringe`, `Awilix`) замість ручного composition root
- `AsyncLocalStorage` з `node:async_hooks` (вбудований)
- Голі `async_hooks` (`AsyncResource`) без ALS
- Лише child-logger Fastify/pino (id тільки в логах)

## Decision Outcome

Обрано "`AsyncLocalStorage` з `node:async_hooks`", бо це вбудований у Node 24 механізм, який дає request-scoped
сховище, ізольоване на часі життя одного запиту, не додає залежностей, не змінює сигнатури сервісів і репозиторіїв та
покриває весь життєвий цикл запиту через `als.run(store, done)` в `onRequest`.

Межі застосування, зафіксовані рішенням:

- Через ALS передаються **лише технічні поля** (`requestId`, `userId`); залежності (репозиторії, `db`, конфіг)
  через ALS **не** передаються — інакше контекст перетворюється на Service Locator і шари злипаються.
- Поза запитом (старт застосунку, seed, юніт-тест сервісу) `getRequestId()` повертає `undefined`, а формат логів
  пише `requestId: '-'`; помилка не кидається — відсутність контексту не повинна ламати бізнес-код.
- ALS імпортується лише в `src/core/context.ts` і плагіні, що його наповнює.

### Consequences

- Добре, бо нуль нових залежностей: `AsyncLocalStorage` — частина `node:async_hooks`.
- Добре, бо сигнатури сервісів і репозиторіїв не містять технічних параметрів — бізнес-логіка не знає про HTTP.
- Добре, бо паралельні запити ізольовані (сховище на кожен async-ланцюг), а синхронний код `node:sqlite` контекст
  не втрачає.
- Добре, бо id доступний і в логах (`mixin`), і в тілі помилки, і в будь-якому майбутньому модулі без параметрів.
- Погано, бо залежність неявна (action at a distance): щоб зрозуміти, звідки id, треба знати про плагін.
- Погано, бо контекст існує лише всередині `als.run(...)`: новий шлях входу без обгортки дасть `undefined` —
  fallback `'-'` рятує логи, але id губиться.
- Погано, бо контекст не перетинає `worker_threads`, черги й колбеки, створені поза контекстом (потрібен
  `AsyncResource.bind`); зараз неактуально, але обмежує майбутнє.
- Погано, бо юніт-тест сервісу, який логує, доводиться обгортати `runWithContext(...)`.
- Погано, бо overhead `async_hooks` не вимірювали — приймаємо за припущенням, профілювання поза обсягом ітерації.
- Нейтрально, бо працює лише в межах процесу — у нас один процес (модульний моноліт, spec-01).
- Нейтрально, бо ALS не керує залежностями: об'єктний граф збирається явно, і це свідоме обмеження рішення.

### Confirmation

- `grep -r "node:async_hooks" src/` → лише `src/core/context.ts` і плагін, що наповнює контекст; у `*.service.ts`,
  `*.repository.ts`, `*.routes.ts` імпортів ALS немає.
- Тест: два паралельні запити з різними `X-Request-Id` — кожен лог-рядок має свій id, змішування немає.
- Тест: сервіс логує id, не отримуючи його параметром (усередині викликає `getRequestId()`).
- Лог старту застосунку (поза запитом) містить `requestId: '-'`, а не `undefined` і не помилку.
- AC-5 зі spec-02 зелений; `npm run typecheck` і `npm run smoke` — без помилок.

## Pros and Cons of the Options

### Явна передача параметрів (prop drilling / parameter threading)

- Добре, бо все явно: видно кожен вхід функції, немає магії.
- Нейтрально, бо для одного-двох полів це ще терпімо.
- Погано, бо технічні деталі просочуються в бізнес-логіку: сервіс приймає id, який не бере участі в правилах.
- Погано, бо кожне нове поле контексту змінює сигнатури в усіх шарах і тестах (2 поля × 3 шари × N методів).

### DI-контейнер зі scoped lifetime (tsyringe, Awilix)

- Добре, бо централізовано керує об'єктним графом і життєвим циклом залежностей.
- Нейтрально, бо наш граф уже закритий ручним composition root без пакетів (spec-02, §2).
- Погано, бо стороння залежність і складніша ініціалізація заради одного request-scoped поля (ADR-0001).
- Погано, бо request-scoped контейнер усе одно спирається на ALS (у документації Awilix є рецепт з
  `AsyncLocalStorage`) — тобто ми беремо той самий механізм без обгортки й зайвого шару, який можна зламати.
- Погано, бо ручний DI без контейнера проблему не вирішує: request-scoped дані все одно треба проносити крізь шари.

### AsyncLocalStorage (обрано)

- Добре, бо вбудований і стабільний у Node 24, без нових залежностей.
- Добре, бо ізолює технічний контекст від бізнес-логіки і не змінює сигнатури.
- Добре, бо `als.run()` в `onRequest` покриває весь запит: хуки, хендлер, `onResponse`-логи та error handler.
- Погано, бо неявний: id «з'являється нізвідки», поки не знаєш про плагін.
- Погано, бо вимагає дисципліни: кожен новий шлях входу (CLI, seed, фонова задача) має сам обгортатися в `run`.
- Погано, бо без типізованого аксесора легко розповзти `any`/`unknown` (у нас — `getRequestId(): string | undefined`).

### Голі async_hooks (AsyncResource без ALS)

- Добре, бо максимальний контроль над життєвим циклом ресурсу.
- Погано, бо низькорівнево й легко помилитися (ручний `enable`/`disable`, власні `Map` для зберігання).
- Погано, бо `AsyncLocalStorage` — це та сама ідея з готовим і протестованим API.

### Лише child-logger Fastify/pino

- Добре, бо нуль коду: pino вже пише `reqId` у кожен лог-рядок запиту.
- Добре, бо закриває головну потребу — логи.
- Погано, бо не дає доступу із сервісів і репозиторіїв (у них немає логера) і не покриває тіло помилки.
- Погано, бо для доступу логер усе одно доведеться передавати параметром — та сама проблема, лише з іншим типом.
