# Сирий SQL через sql-template-tag замість ORM для доступу до node:sqlite

## Context and Problem Statement

ADR-0001 обрав `node:sqlite` (`DatabaseSync`, синхронний API, без native-збірки). Лишилося вирішити, **як формувати
SQL і мапити рядки**: потрібні параметризація значень (безпека), явні JOIN-и й контрольована кількість запитів
(AC-7), транзакції та ретраї всередині DAO (spec-02 §1–§3, §9) і мінімум залежностей (ADR-0001). Питання: сирий SQL,
query builder чи ORM? Драйвер БД цим ADR не переглядається — лише шар формування запитів.

## Decision Drivers

- Захист від SQL-ін'єкцій у значеннях: параметризація має бути структурною, а не «на совість».
- Видимість SQL і кількості запитів: JOIN-и явні, N+1 не виникає непомітно.
- Сумісність зі `StatementSync`: `?`-плейсхолдери й `values` без адаптерів.
- Мінімум залежностей і ESM-сумісність (ADR-0001, `type: module`).
- SQL як джерело істини: рев'ю, `EXPLAIN QUERY PLAN`, навчальна цінність.
- Транзакції лишаються в DAO (`db/transaction.ts`), без UnitOfWork, сесій та identity map.

## Considered Options

- ORM (TypeORM)
- Query builder (Kysely)
- Сирий SQL із ручними `?`-плейсхолдерами й масивом значень
- Сирий SQL + `sql-template-tag`
- Інша тег-бібліотека (`sql-template-strings`, `@databases/sql`)

## Decision Outcome

Обрано "сирий SQL + `sql-template-tag`", бо пакет параметризує кожне інтерполювання, дає композицію фрагментів і
`join()` для `IN (...)`, не має жодних транзитивних залежностей, сумісний з ESM (`type: module`) і віддає
`{ sql, values }`, що лягає 1:1 у `db.prepare(sql).all(...values)` для `node:sqlite`.

Правила, зафіксовані рішенням:

- SQL будується лише через `sql`-тег; конкатенація рядків і підстановка значень у текст заборонені.
- `raw()` — лише для статичних фрагментів; динамічні ідентифікатори (`ORDER BY`, назви колонок) — тільки з
  whitelist, ніколи з тіла запиту (README пакета прямо попереджає про ін'єкцію через `raw`).
- `values` у пакеті типізовані як `unknown`, тому в `src/db/` живе тонка типізована обгортка над тегом
  (`null | number | bigint | string | Uint8Array` — те, що приймає `node:sqlite`); модулі імпортують обгортку, а не
  пакет напряму.
- Транзакції й ретраї — не властивість бібліотеки: `BEGIN IMMEDIATE … COMMIT/ROLLBACK` у `src/db/transaction.ts` і
  `withRetry` навколо транзакції (spec-02, §9).

### Consequences

- Добре, бо нуль транзитивних залежностей: у `sql-template-tag@5.2.1` порожній `dependencies`, пакет ESM-only, тобто
  збігається з нашим `type: module`.
- Добре, бо параметризація структурна: кожен `${value}` стає `?`, значення їдуть окремим масивом — ін'єкція в
  значеннях закрита конструктивно, а не домовленістю.
- Добре, бо фрагменти композиційні: вкладені `sql`-вирази, `join(ids)` для `IN (...)` (потрібно для 2-запитної
  видачі коментарів, AC-7) і `empty` для опційних умов — без ручного склеювання `?`.
- Добре, бо кількість запитів видима в коді: lazy-relations немає, JOIN-и явні, тож N+1 не виникає непомітно (в ORM
  relations/eager/lazy генерують запити самі).
- Добре, бо `{ sql, values }` не потребує адаптера: `?`-плейсхолдери підтримує `StatementSync`.
- Погано, бо немає компіляційної перевірки SQL: друкарська помилка в назві колонки ловиться лише запуском і тестами.
- Погано, бо мапінг `rows → домен` ручний у кожному репозиторії (разом із `snake_case` → `camelCase`), ORM цього не
  робить за нас.
- Погано, бо `values` типізовані як `unknown` → потрібна власна обгортка, інакше розповзеться `any` (заборонено DoD).
- Погано, бо немає relations, каскадів на рівні моделі, міграцій і change-tracking: усе це робимо SQL-ом і руками.
- Погано, бо треба знати SQL і діалект SQLite (`CHECK`, `FOREIGN KEY`, `PRAGMA`) — поріг входу вищий, ніж в ORM.
- Нейтрально, бо параметри анонімні (лінійний масив), а не іменовані (`:name`) — читабельність трохи гірша.
- Нейтрально, бо SQL стає джерелом істини: зміна схеми й запитів рев'юється в одному діфі, без «магії» моделі.

### Confirmation

- `grep -r "sql-template-tag" src/` → лише `src/db/**` і `src/modules/*/*.repository.ts`.
- `grep -rn "raw(" src/` → 0 входжень або лише статичні рядки без інтерполяції; `raw` з даними запиту — блокуючий
  коментар на рев'ю.
- `npm ls --depth=0` → у `dependencies` рівно `fastify` і `sql-template-tag`, без транзитивних залежностей.
- Тест: `POST /tickets` із `title: "'; DROP TABLE tickets; --"` → 201, значення збережене як текст, таблиця на місці.
- AC-7: `GET /tickets` виконує рівно 2 SQL-запити незалежно від кількості тикетів (лічильник у тесті).
- `npm run typecheck` зелений, тобто обгортка не пропускає `any` у `values`.

## Pros and Cons of the Options

### ORM (TypeORM)

- Добре, бо entities, relations і міграції з коробки, типізація колонок.
- Нейтрально, бо для трьох таблиць і десяти сценаріїв це надлишковий шар.
- Погано, бо офіційного драйвера під `node:sqlite` немає: для SQLite TypeORM підтримує `better-sqlite3`, `sql.js` і
  мобільні драйвери (перевірено 2026-10-23) — це або native-збірка, або другий SQLite-драйвер, що суперечить
  ADR-0001.
- Погано, бо relations/eager/lazy генерують запити самі: N+1 стає непомітним, а кількість запитів доводиться
  вимірювати окремо.
- Погано, бо `reflect-metadata`, декоратори й `synchronize` додають магію, яку важко показати на захисті.

### Query builder (Kysely)

- Добре, бо типізований builder без entities й `reflect-metadata`, SQL лишається видимим.
- Нейтрально, бо для `node:sqlite` потрібен core `SqliteDialect` (він про `better-sqlite3`) або community-діалект
  `kysely-node-native-sqlite`.
- Погано, бо це +1 залежність (плюс діалект), а community-діалект ми не контролюємо: закинутий = глухий кут.
- Погано, бо для двох JOIN-ів і десяти запитів виграш у типізації не окуповує новий шар абстракції.

### Сирий SQL із ручними `?` і масивом значень

- Добре, бо нуль залежностей і максимальна прозорість.
- Добре, бо саме так працює `StatementSync` — без адаптерів.
- Погано, бо порядок `values` легко переплутати з порядком `?` (особливо в динамічних умовах), і це ловить лише тест.
- Погано, бо `IN (...)` та опційні умови доводиться склеювати вручну (`map(() => '?')`), що і є джерелом помилок та
  ін'єкцій при необережному рефакторингу.

### Сирий SQL + sql-template-tag (обрано)

- Добре, бо `${value}` автоматично стає `?` + `values` — параметризація структурна, а не «на совість».
- Добре, бо фрагменти композиційні: вкладені `sql`, `join` для `IN`, `empty` для опційних умов.
- Добре, бо нуль транзитивних залежностей, ESM, 6 файлів ≈ 20 KB — ціна мінімальна.
- Погано, бо `raw()` існує — потрібна дисципліна і `grep`-перевірка (README прямо попереджає про ін'єкцію).
- Погано, бо `values: unknown` → потрібна власна типізована обгортка (кілька рядків у `src/db/`).

### Інша тег-бібліотека (sql-template-strings, @databases/sql)

- Добре, бо ідея та сама: безпечні шаблонні рядки замість конкатенації.
- Погано, бо `sql-template-strings` просуває мутацію через ланцюжок методів і не підтримує вкладені SQL-вирази (за
  README `sql-template-tag`).
- Погано, бо `@databases/sql` орієнтований на власну екосистему драйверів і має ширший API, ніж нам потрібно;
  виграшу проти обраного варіанта немає.
